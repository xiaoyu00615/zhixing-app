# 0. 技术选型结论

本项目采用“一套 React / TypeScript 业务 UI + 多平台 Adapter + 本地数据库”的架构。

当前技术基线：

| 前端核心 | React 19.2 + React DOM | Web / Desktop / Android 共用 UI |
| 类型系统 | TypeScript strict | 领域对象、Repository、Adapter、DTO、同步协议 |
| 构建 | Vite 8.x | Dev / Build |

# 1. 总体架构

```text
React UI
   ↓
Application Service
   ↓
Repository Interface
   ↓
┌──────────────────────────────┐
│ Native Adapter               │
│ Web Adapter                  │
│ Test / Memory Adapter        │
└──────────────────────────────┘
   ↓
SQLite / OPFS / File System / System API
```

核心原则：

- UI 不知道底层数据库实现；
- Native 与 Web 共用领域模型和 Repository Contract；
- 平台差异通过 Adapter / Platform Service；
- 高风险数据操作集中到专门 Service / Rust，不散落页面；
- 测试可替换 TestRepository。

# 2. 前端工程

## 2.1 React + TypeScript + Vite

React 负责组件和页面；TypeScript 必须开启 strict；Vite 作为唯一前端构建入口。

不采用 Next.js / Vue / Angular，除非用户批准技术变更。项目不依赖 SSR / SEO / Server Rendering。

## 2.2 React Router 8

使用 Declarative Mode 作为 SPA 基线。

建议主路由：

```text
/today
/tasks
/canvas
/canvas/:canvasId
/diary
/notes
/search
/tags
/archive
/trash
/settings/*
```

Router 只负责导航与 URL 状态，不直接承担 SQL 访问。

## 2.3 Tailwind CSS + Design Tokens

所有颜色、间距、圆角、尺寸从《UI设计规范 V1.2》映射成 CSS Variables / Tailwind Theme。

禁止页面中反复写随机 magic number 代替 Token。

## 2.4 shadcn/ui + Lucide React

shadcn/ui 组件源码进入项目，自行按规范调整，不作为黑盒 UI SaaS Kit。

Lucide React 是唯一主图标体系。

## 2.5 Zustand

只保存：

- Sidebar / Drawer / Modal；
- 当前筛选；
- Canvas 当前选择态；
- 临时 UI 草稿；
- 非持久交互状态。

业务事实来源仍为 Repository / SQLite，不把全部 Task / Document 长期塞进 Store。

## 2.6 React Hook Form + Zod 4

React Hook Form 管理表单 dirty / touched / errors / submit；Zod 负责：

- 用户输入；
- Import 数据；
- Settings；
- Node Content Schema；
- Sync Payload；
- Backup Manifest。

# 4. 领域模型基线

所有核心同步型实体原则上：

```text
id: UUID
created_at
updated_at
deleted_at
revision
device_id
```

需要 Archive 的实体优先评审 `archived_at nullable`。

## 4.1 Task

业务字段方向：

```text
title
description / content
status: todo | doing | completed | cancelled
due_at
importance
urgency
project_id nullable
```

Overdue 动态计算，不存为 status。

Task 的 Importance 与 Urgency 分离；Overdue 只允许影响 Urgency 逻辑，不修改 Importance。

Subtask 模型与 Timeline 是否需要 `start_at` 在 Phase 0 决定。

## 4.2 Project

Task 内部轻量分组实体，不做一级导航。

字段方向：

```text
id
name
color
sort_order
created_at
updated_at
deleted_at
revision
device_id
```

## 4.3 CaptureItem

快速捕捉实体，承接首页 Quick Capture。

字段方向可考虑：

```text
id
content / plain_text
source_type
created_at
updated_at
deleted_at
revision
device_id
```

“转换为 Task / Note / Diary / Canvas”优先通过 Application Service 完成，不在 CaptureItem 里嵌入完整目标实体。

## 4.4 Document

Diary / Note 共用核心模型：

```text
id
type: diary | note
title（Diary 是否必需待评审）
content_json
plain_text
created_at
updated_at
deleted_at
revision
device_id
```

Diary 专属逻辑日期：`diary_date`。

Note Folder、Favorite 具体物理字段在 Phase 0 决定。

Tag / Attachment 不使用 `tag_ids[]` / `attachment_ids[]` 嵌入数组，使用关系模型。

## 4.5 Canvas / CanvasNode / CanvasEdge

```text
Canvas
- id
- title
- viewport_json
- created_at / updated_at / deleted_at / revision / device_id

CanvasNode
- id
- canvas_id
- type
- x / y
- content_json
- linked_entity_type nullable
- linked_entity_id nullable
- created_at / updated_at / deleted_at / revision / device_id

CanvasEdge
- id
- canvas_id
- source_node_id
- target_node_id
- label nullable
- style_json nullable
- relation_type nullable (future extension)
- created_at / updated_at / deleted_at / revision / device_id
```

Node Type V1：text / sticky / image / link / task / note / diary。

`content_json` 必须使用 Discriminated Union / Zod Schema 等方式按 Node Type 类型化。

关联实体节点不复制完整 Task / Note / Diary；`linked_entity_type + linked_entity_id` 是关联真值。

关联实体 Soft Delete 不级联删除 Node。

## 4.6 Tag / Attachment / EntityLink

Tag = 跨模块用户标签。

Attachment metadata 基线统一：

```text
id
hash
filename
mime
size
relative_path
created_at
updated_at
deleted_at
revision
device_id
```

实际文件由 StorageAdapter 保存。

EntityLink 用于通用实体关系，但 Tag 物理关联是否共用 EntityLink 还是独立 junction table，要在 Phase 0 以查询性能、约束和迁移复杂度评审后批准。

# 5. React Flow / Canvas 技术

使用 `@xyflow/react` 作为 Infinite Canvas 视图交互层。

React Flow 负责：Node / Edge / Viewport / Selection / Drag / Zoom / MiniMap / Custom Node。

Repository 负责业务持久化。

Undo / Redo：

```text
UI Command
→ Session History Stack
→ State Mutation
→ debounce / transaction save
→ Repository
```

V1 不要求把每一步 Undo History 永久写入数据库。

Group V1：组合 / 整体移动 / 取消组合，不提前锁定整体缩放。

AI 不在 Phase 3；最多保留 AIAdapter / UI Placeholder。

# 6. Tiptap / Document 技术

Tiptap 3 作为 Diary / Note / Task Description 的富文本核心。

保存：

- `content_json` 用于完整恢复；
- `plain_text` 用于 FTS / Preview / AI。

自动保存：

```text
Editor Change
→ Dirty State
→ Save Queue / Debounce
→ DocumentService
→ Repository
→ Local Save Status
```

具体 debounce 数值不在规范写死，由 Phase 4 性能测试确定。

不依赖 `beforeunload` 作为核心数据安全机制；适当生命周期事件应尝试 flush pending writes。

# 7. Native：Tauri 2 + Rust

Tauri 2 包装共享前端，Windows 与 Android 通过同一工程发展。

Tauri Capability 按最小权限配置。

React 只能访问明确授权的 Command / Plugin API。

高风险能力优先放在 Rust / Platform Service：

- 安全数据位置迁移；
- Backup / Restore；
- Hash / Integrity；
- LAN Sync；
- 文件系统权限边界。

Native SQLite CRUD 可通过 Tauri SQL Plugin / Rust 数据服务实现，但最终数据驱动方案需在 Phase 0 验证 Windows + Android 支持、Migration、Backup API 和测试便利性后冻结。不得同时建立两套互相竞争的通用 Repository 数据层。

# 8. Native SQLite

SQLite 是 Native 核心事实来源。

要求：

- Foreign Keys；
- Transaction；
- Migration；
- FTS5；
- 本机文件系统；
- 合理使用 WAL；
- 不放 NAS / SMB 作为实时主库。

Schema 变更只走 Migration，例如：

```text
001_initial.sql
002_add_project.sql
003_add_capture_item.sql
004_add_archive_fields.sql
```

禁止“启动时如果字段不存在就临时 ALTER”的散乱逻辑。

# 9. Web：SQLite WASM + OPFS

Phase 1B 必须落地真实 Web Persistence。

架构：

```text
React
→ Web Repository Adapter
→ Database Worker
→ SQLite WASM
→ OPFS
```

原则：

- DB 运算放 Worker，避免阻塞 UI；
- Web 与 Native 不是同一个 sqlite 文件；
- Repository Contract 对上层一致；
- OPFS 不可用时给明确提示 / 受限模式；
- 不静默降级到易丢失存储。

# 10. Search 技术

使用 SQLite FTS5 作为本地全文搜索核心，不引入 Elasticsearch / Meilisearch 等服务器搜索引擎。

FTS 基线：

- Task title / description；
- Canvas title；
- CanvasNode 可检索文本；
- Note title / plain_text；
- Diary title / plain_text；
- CaptureItem plain_text。

Tag / Project / Status / Date / archived_at 属于结构化 Filter，使用普通 SQL / Join / WHERE，不强塞给 FTS。

Global Search 默认排除 `deleted_at IS NOT NULL` 的 Trash 内容。

Ctrl+K Command Palette 不走完整 Global Search UX。

# 11. Attachment / File Storage

附件实际文件不作为大量 SQLite BLOB。

StorageAdapter 决定真实存储位置。

数据库只存 metadata 和设备本地 `relative_path`。

SHA-256 用于：

- 完整性验证；
- 去重辅助；
- Backup；
- Sync Missing File Detection。

不同设备不要求拥有相同 `relative_path`。

# 12. Storage 目录

简单模式建议：

```text
ZhixingData/
├─ database/
├─ attachments/
├─ thumbnails/
├─ backup/
└─ metadata/
```

高级模式允许分开设置 Database / Attachments / Backup / Cache。

Data Root Manifest 与 Backup Manifest 分离。

Data Root Manifest 描述当前数据目录结构与版本；Backup Manifest 描述某次 Backup 的文件清单、Hash、Schema / App / Format 版本。

# 13. 安全数据位置迁移

不得直接修改路径字符串，也不得依赖直接复制运行中的 sqlite / wal / shm。

基线流程：

```text
Validate Target
→ Check Space
→ Pause Writes
→ Flush Pending Writes
→ Create SQLite Safety Snapshot
→ Copy to Temporary Target
→ Verify Hash + SQLite integrity_check
→ Reopen Target
→ Verify Attachments
→ Commit Path Switch
→ Keep Old Data Until User Confirms
```

Phase 6 决定具体使用 SQLite Backup API、checkpoint、`VACUUM INTO` 或等价安全机制。

若数据位置失效，禁止自动创建空数据库。

# 14. Backup

完整 Backup 基线：

```text
Database
Attachments
Portable Settings
Backup Manifest
```

Portable Settings 与 Device-local Settings 分离。

不得从 Backup 无脑恢复：

- device_id；
- 本机绝对路径；
- Trust Token；
- Pairing Credential；
- 本机权限状态；
- 其他 Device-local 配置。

# 15. Restore

优先 Staging Restore：

```text
Select Backup
→ Validate Manifest
→ Verify Hash
→ Create Current Safety Snapshot
→ Unpack to Staging
→ Validate Database / Attachments
→ Reopen Staging Data
→ Final Verification
→ Switch to Restored Data
```

恢复失败时原正式数据必须保持可恢复。

# 16. Archive / Trash 数据生命周期

推荐评审方向：`archived_at nullable`。

```text
Normal
<-> Archive
Archive Delete → Trash
Normal Delete → Trash
Trash Restore → Previous Logical State
Trash Permanent Delete → Physical Delete
```

Permanent Delete 只从 Trash 发生。

V1 默认不执行“30 天自动物理清空”等破坏性策略。

# 17. Device Sync（Phase 7）

正式实现前只预留接口。

拓扑：

```text
Peer A Local SQLite
       <->
    Sync Engine
       <->
Peer B Local SQLite
```

没有默认主设备。

核心同步概念：

- Device；
- SyncChange；
- Revision；
- Cursor；
- Tombstone；
- Conflict；
- Attachment Hash。

Pair Code / QR 是临时配对凭证。

设备身份 = stable device_id + trust identity；IP 不是身份。

不使用社交 Presence 设计。

不可安全自动合并的内容进入 Conflict，不默认静默 Last Write Wins。

Remove Device = Revoke Trust，不远程删除另一设备数据。

Attachment Sync：metadata + hash + bytes；目标设备通过 StorageAdapter 决定本地路径。

网络实现方向可在 Phase 7 评审 Tokio / Axum / HTTP / WebSocket / Serde / mDNS 等具体组合，不在 Phase 1–6 提前侵入业务页面。

# 18. Settings 技术分类

Settings 数据必须区分：

- Portable User Preferences；
- Device-local Configuration。

设置 Repository / Service 不允许把所有配置放一个无法区分生命周期的大 JSON 然后跨设备全量覆盖。

# 19. 错误、日志与恢复

前端：React Error Boundary + 统一 App Error Model。

Rust：结构化 logging / tracing。

错误必须可分类：

- Validation；
- Storage Unavailable；
- Database；
- Migration；
- Backup；
- Restore；
- Sync；
- Permission；
- Unknown。

数据位置不可用时属于 Storage Unavailable，不得伪装成“新用户空数据”。

# 24. TRAE 不可违反技术规则

1. React + TypeScript + Vite 为共享前端基础。
2. Native 用 Tauri 2，不改 Electron。
3. React Component 不直接执行 SQL。
4. Zustand 不作为业务数据库。
5. Schema 变更必须走 Migration。
6. 核心 ID 使用 UUID。
7. Task status / Importance / Urgency / Overdue 分离。
8. Canvas 必须 Canvas / Node / Edge 拆分；sticky 不遗漏。
9. Tiptap 保存 content_json + plain_text。
10. Attachment 文件系统保存，SQLite 只存 metadata。
11. Document / Tag / Attachment 使用关系，不存 ID 数组字段。
12. Web Phase 1B 必须真实持久化，不用 Mock 代替主验收。
13. 数据位置迁移必须 Safety Snapshot + Verify。
14. Restore 必须 Staging + Safety Snapshot。
15. Backup 不覆盖 Device-local identity / trust 配置。
16. Archive 不直接永久删除；Permanent Delete 只从 Trash。
17. LAN Sync 只在 Phase 7 正式实现。
18. Device Sync 无默认主设备；IP 不是身份。
19. Conflict 不默认静默 Last Write Wins。
20. Attachment Sync 不同步跨设备实际路径。
21. 任何“完成”声明必须附真实测试结果。
22. UI 实现以 V1.2 Token 为准，PNG 只作视觉参考。
