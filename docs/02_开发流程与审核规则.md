# 02｜开发流程与审核规则

版本：V1.1  
日期：2026-08-19  
状态：CURRENT

## 1. 总体流程

所有任务统一采用：

```text
Read
→ Understand
→ Review
→ Plan
→ Review
→ Implement
→ Test
→ Fix
→ Re-test
→ UI Compare
→ Report
→ Human Acceptance
→ DONE
```

Agent 的速度不得优先于可审计性与数据安全。

## 2. 每轮开始前必须读取

至少读取：

1. `/project_rules.md`；
2. `/docs/00_当前版本清单.md`；
3. 当前 Phase 计划；
4. 最新 UI 规范；
5. 最新技术规范；
6. 当前模块冻结设计图；
7. 当前模块已有代码；
8. 相关 Migration / Repository / Test。

禁止使用 `/docs/archive/` 中历史版本作为当前真值。

## 3. 第一步：需求理解

收到任务后不要立即改代码，先回复：

```text
【需求理解】

本阶段目标：
涉及模块：
需要新增：
需要修改：
明确不处理：
依赖：
风险：
需要确认：
```

用户审核通过后进入计划。

## 4. 第二步：实施计划

提交：

```text
【实施计划】

Step 1：
Step 2：
Step 3：

预计新增文件：
预计修改文件：
预计数据库变更：
预计新增 Migration：
预计新增测试：
预计运行命令：
可能风险：
需要用户批准：
```

以下属于重大决策，必须先批准：

- 技术栈变更；
- 核心架构变更；
- 核心 Schema 变更；
- UI 基础规范变更；
- 公共 Adapter / Repository 接口破坏性变更；
- Phase 边界变更；
- 数据生命周期 / 同步 / Backup 安全策略变更。

## 5. 第三步：开始实现

只有用户明确回复“计划通过，可以开发”或等价表达后才能修改代码。

实现规则：

- 只改当前任务必要内容；
- 不顺手大规模重构；
- 不提前开发未来 Phase；
- 不自行添加未批准功能；
- 不删除重要文件而不说明；
- 先小步完成，再运行测试。

## 6. 第四步：自动测试

根据当前任务执行适用项：

- TypeScript typecheck；
- ESLint / formatter check；
- Unit Test；
- Component Test；
- Repository / Integration Test；
- Migration Test；
- Web Build；
- Web Preview；
- Playwright E2E；
- Tauri Check / Build；
- `cargo test`；
- Windows Smoke Test；
- Android Smoke Test（涉及时）。

测试没运行不得标 PASS。

## 7. 第五步：失败处理

测试失败必须：

```text
发现失败
→ 读取完整错误
→ 分析原因
→ 最小修复
→ 重跑失败测试
→ 重跑受影响回归测试
```

无法继续时输出：

```text
【阻塞问题】

失败项目：
错误信息：
已经尝试：
判断原因：
可选方案：
推荐方案：
需要用户决定：
```

然后停止扩展开发。

## 8. 第六步：UI 实际运行检查

涉及 UI 时必须实际运行，不允许只读源码判断。

至少验证：

- 1920 × 1080；
- 1440 × 900；
- 1280 px 最低桌面宽度的核心可操作性。

检查：

- Sidebar / Topbar；
- 页面 Padding；
- 字体层级；
- Card / Table；
- Modal / Drawer；
- Hover / Focus / Disabled；
- 关键按钮 Pressed；
- Empty / Loading / Error；
- 滚动 / 溢出；
- 键盘操作；
- 可访问性基础要求。

1920 与 1440 默认优先保持首页 KPI 四列；更窄断点不得自行发明，需实际验证和审核。

## 9. 第七步：设计稿对照

输出：

```text
【设计稿对照】

整体布局：PASS / DIFF
组件尺寸：PASS / DIFF
字体层级：PASS / DIFF
颜色：PASS / DIFF
间距：PASS / DIFF
交互：PASS / DIFF
响应式：PASS / DIFF
需修复项：
```

PNG 只用于视觉关系，不测量图片像素反推 CSS。

## 10. 第八步：开发报告

每轮结束必须输出：

```text
【本轮开发报告】

一、本次目标
二、已完成内容
三、新增文件
四、修改文件
五、数据库 / Migration 变更
六、测试结果

Type Check：
Lint：
Unit Test：
Integration Test：
Migration Test：
E2E：
Web Build：
Tauri：
Rust Test：
Native Smoke：

七、UI 验证
1920×1080：
1440×900：
1280：

八、已知问题
九、技术债
十、风险
十一、建议下一步
```

没有执行的项目必须写 `NOT RUN` / `NOT APPLICABLE`，不能假装 PASS。

## 11. 第九步：人工验收

开发报告提交后停止，等待用户实际查看：

- 页面；
- 功能；
- 数据；
- 重启恢复；
- UI；
- 测试报告。

用户明确“审核通过”后才进入 DONE。

## 12. 数据库与 Migration 额外审核门禁

涉及 Schema / Migration 时，Agent 计划必须说明：

- 新增 / 修改字段；
- 是否 nullable；
- 默认值；
- 旧数据迁移方式；
- 回滚 / 失败处理；
- 索引；
- FTS 影响；
- Soft Delete / archived_at 影响；
- 同步字段 revision / device_id 影响。

不得在页面组件里用临时 SQL 修 Schema。

## 13. 高风险数据操作额外门禁

涉及 Migration、数据位置迁移、Backup、Restore、Permanent Delete、Sync Conflict 时：

1. 先提交技术风险；
2. 明确安全快照 / Staging / Integrity 方案；
3. 写自动测试；
4. 再开发；
5. 实测失败路径；
6. 人工验收后才 DONE。

## 14. UI 图片提供与审核规则

UI 图片按模块使用，不一次把所有图片作为当前实现上下文。

建议一次 1–3 张，同一模块最多约 4 张，并明确每张职责。

图片理解报告必须区分：

- 已批准产品规则；
- UI 视觉示例；
- 当前 Phase 功能；
- 未来能力；
- 未确定事项。

四批现有 UI 已 FROZEN，不需要再次自行解释或重构其产品含义。

## 15. 文档版本规则

每轮开发先读取 `/docs/00_当前版本清单.md`。

如果存在 V1.0 / V1.1 / V1.2 等多个版本：只执行 CURRENT；旧版移入 archive 后自动降级为历史参考。

## 16. Git 规则

推荐：

```text
feature
→ test
→ fix
→ review
→ approved
→ commit
```

Commit 示例：

```text
feat(task): complete task module MVP
feat(canvas): implement canvas editor foundation
fix(task): correct overdue calculation
chore(db): add schema migration 003
```

未验收的大型修改不要用“complete”类 commit message。

## 17. 删除规则

删除重要文件前先报告：

```text
需要删除：
原因：
影响：
替代方案：
恢复方式：
```

未经批准不得删除 Migration、用户数据、Backup、规范、核心配置等重要内容。

## 18. 决策边界

Agent 可以自主决定小型实现细节，例如局部函数拆分、非破坏性命名、测试文件组织。

必须由用户批准：产品逻辑、数据模型、架构、同步策略、数据安全策略、技术栈、主 UI 结构、Phase 顺序。
