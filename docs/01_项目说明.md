## 1. 产品概述

“知行｜个人知识与行动中枢”是一款单用户、本地优先、离线优先的个人效率与知识管理软件。

目标不是只做 Todo，也不是做多人协作平台，而是形成个人信息从“捕捉”到“执行、整理、检索、再次利用”的完整闭环。

核心信息流：

```text
快速捕捉
→ 梳理
→ 转为 Task / Note / Diary / Canvas
→ 执行或沉淀
→ 搜索 / 关联 / 回看
→ 再利用
```

## 2. 核心产品理念

### Capture

任何碎片信息都能先记下来，不要求用户立即决定它最终属于什么。

### Connect

Task、Note、Diary、CanvasNode、CaptureItem 等内容可以通过关系建立联系。

### Convert

CaptureItem 和部分 Document 内容可以转化或关联到 Task、Note、Diary、Canvas。

### Local First

核心功能不依赖网络、账号、云服务。网络只用于未来自己的设备之间同步等扩展能力。

### Data Ownership

用户可以查看、迁移、备份、恢复自己的本地数据位置，不被单一云服务绑定。

## 3. 核心模块

### 3.1 首页 / Today

首页只负责“看今天”和快速进入下一步。

主要内容：

- 问候与日期；
- 4 个 KPI 摘要；
- 今日重点任务；
- 今日日程；
- 最近 CaptureItem；
- 最近 Note；
- 最近 Canvas；
- 快速记录。

首页不是完整任务系统，不放完整四象限、完整月历、完整 Canvas 编辑器。

首页快速记录位于正常文档流最后一块，不是 Sticky Footer。设计图中展示条目数量只属于视觉示例，不是数据库硬限制。

### 3.2 CaptureItem / QuickCapture

`CaptureItem` 是独立轻量实体，承接“先记下来、稍后整理”的碎片内容。

可以后续：

- 转为 Task；
- 转为 Note；
- 转为 Diary；
- 添加到 Canvas；
- 与现有实体建立关联。

如保留 `@` 语义，只表示引用本地实体，不表示人员 Mention。

### 3.3 Task

一级视图：

- 列表；
- 四象限；
- 日历；
- 时间线。

核心能力：

- CRUD；
- status：todo / doing / completed / cancelled；
- Importance；
- Urgency；
- Deadline；
- Overdue 动态计算；
- Project；
- Tag；
- Task Detail Drawer；
- Create/Edit Modal；
- 软删除与恢复；
- 关联 Note / Diary / Canvas。

Project 是 Task 内部轻量分组实体，不做一级导航。

Importance 与 Urgency 分离。Overdue 可以影响 Urgency，但不自动修改 Importance。

Archive 不是 Task status。

Timeline 具体交互当前未冻结为甘特图，不因 Timeline 自动增加 `start_at`。

### 3.4 Canvas

正式产品拆成：

1. Canvas List；
2. Canvas Editor。

初始 Node Types：

- text；
- sticky；
- image；
- link；
- task；
- note；
- diary。

组织与编辑能力：

- Edge；
- Group；
- 多选；
- Copy / Paste；
- Undo / Redo；
- Zoom / Pan；
- MiniMap；
- 当前画布搜索；
- 按需 Node Property Panel。

AI 整理属于未来 Phase 8，不是 Phase 3 实现内容。

### 3.5 Diary

Diary 强调按日期记录和回看。

主要入口：

- 今天；
- 日历；
- 时间线；
- 智能日记夹 / Saved View。

Diary 使用独立逻辑日期 `diary_date`，与创建时间分离，支持补写过去日期。

智能日记夹是本地规则筛选，不是 Note Folder，不依赖 AI。

### 3.6 Note

Note 强调知识编辑、整理、关联、检索。

主要能力：

- Note List；
- Folder；
- Tag；
- Favorite；
- Tiptap 富文本编辑；
- Attachment；
- Related Content；
- Local Auto Save。

Folder 与 Tag 区分：Folder 是 Note 内部组织；Tag 是跨模块分类。

Note 与 Diary 是独立 domain：独立 repository、独立 service、独立 persistence contract（各自 `src/note/*` 与 `src/diary/*`）。两者不共用 canonical Document 实体；未来共享的 Tag / Attachment / Relation capability 不等于建立 Generic Document / DocumentRepository / DocumentService。产品页面与使用目的保持独立。

### 3.7 Global Search

Global Search 是独立本地全文搜索中心，不等于 Ctrl+K。

当前 Global Search V1 真实实体范围（已实现，非 aspirational）：

- Task（仅 title）；
- Note（title + content）；
- Diary（title + content）；
- Canvas（仅 title）。

当前不包含（不得描述为 V1 已实现）：

- CanvasNode（future / planned）；
- CaptureItem（future / planned）；
- Tag（future / planned）；
- Archive（archived Task / Note 被普通 Search 排除；future / planned）；
- Trash（软删除实体被排除）。

Attachment metadata 后续可扩展。

Project 是筛选维度；Favorite 是属性 / 特殊视图，不是实体类型。

Ctrl+K 保留给 Command Palette：快速导航、快速命令、快速创建、最近访问。

### 3.8 Tag

Tag（标签）是用户自定义标记，用于归类实体。

当前 Tags V1（CLOSED）范围：仅 Task-only —— 创建 / 列出 / 重命名标签，给 Task 添加 / 移除标签，按标签过滤 Task；Native（Rust / SQLite）与 Web（共享 Worker / sqlite-wasm / OPFS）对称实现，reload 后存活。

长期方向（future / planned，不在 V1 范围）：跨模块标签（Note / Diary / Canvas / CaptureItem）、标签颜色、标签合并、标签删除、Tag Search 索引、独立 TagsPage。这些在当前阶段均为未来增强，不作为 Phase 5 完成阻塞项。

Tag 不等于 Project、Folder、Badge、Status。

### 3.9 Archive

Archive 是独立数据生命周期能力，不是 Task / Note 的 status（`archived_at_ms` 与 `status` 正交）。

Archive V1 实体范围：Task + Note。

规则：

- 归档内容从主要工作页面（Task / Note 列表）隐藏；
- 普通 Global Search 排除 archived Task / Note；
- Unarchive 恢复 active 状态并恢复 Search 投影包含；
- Archive 中执行 Delete 进入 Trash（不允许从 Archive 直接物理永久删除）；
- Trash Restore 保留 archived 状态，回到 Archive（仍不出现在普通 Search）。

Diary / Canvas：Archive V1 未实现（future / planned）。

### 3.10 Trash

Trash 展示 Soft Delete 内容。

支持：

- 恢复；
- Permanent Delete；
- 批量恢复；
- 清空 Trash（强确认）。

Global Search 默认排除 Trash 内容。V1 不默认自动物理清空核心数据。

### 3.11 数据与存储

产品方向（含未来）：

- 当前数据位置查看；
- 打开所在文件夹；
- 简单模式 / 高级模式；
- 安全迁移；
- 数据位置失效恢复；
- Attachment 管理；
- Cache 清理；
- 导入 / 导出。

简单模式只让用户选择一个数据根目录；高级模式才拆分 Database / Attachments / Backup / Cache。

#### 当前已实现（Native / Windows）

- 数据根目录由 `bootstrap.json` 记录；`device_id` 与 bootstrap version 在其中持久化，且在迁移过程中保持不变；
- **Native Simple Data Root Migration V1**：整根迁移（`manifest.json` + `database` / `attachments` / `thumbnails` / `backup` / `metadata`）→ 迁移前 Safety Backup → copy manifest（relativePath / sizeBytes / SHA-256）→ 空间预检 → staging → 单次 rename 原子发布 → 原子 bootstrap 切换 → 失败可回滚 → 旧数据根全量保留 → 进程崩溃启动恢复 → 下一条生产命令走新数据根；
- 迁移过程中 `attachments/` 目录字节被完整保留。

#### 当前未实现（planned / future）

- 高级模式分路径（Database / Attachments / Backup / Cache 拆分配置与迁移）；
- Attachment 管理能力（当前尚无共享 Attachment / File Asset contract、无 production attachment writer、无 attachment hash ownership）；
- Cache 清理；
- 导入 / 导出；
- 数据位置查看 / 打开所在文件夹 / 数据位置失效恢复的产品 UI；
- Web 侧与 Android 侧的数据位置迁移。

> 迁移保留 `attachments/` 字节 **不等于** Attachment 能力已实现。

### 3.12 Backup / Restore

Backup 是数据安全能力，不等于 Sync。

产品方向（含未来）：

- Manual Backup；
- Auto Backup；
- Backup History；
- Restore；
- Restore 前 Safety Snapshot；
- Staging Restore；
- Manifest / Hash / Integrity Check；
- Portable Settings Backup / Restore。

#### 当前已实现（Native / Database-only）

- Native **Database** Backup V1：SQLite Online Backup API + manifest + SHA-256 + `integrity_check` + staging 原子发布；
- Native Backup Inventory：`INCOMPLETE` / `INVALID` / `UNSUPPORTED` / `STRUCTURALLY_VALID` 四态分类；
- Native Backup Verification：显式 verify、streaming SHA-256、read-only `integrity_check`；
- Native **Database** Restore V1：Restore 前 Safety Backup → staging → 原子替换 → 失败回滚 → IPC 协调与崩溃启动恢复。

#### 当前未实现（planned / future）

- Attachment Backup / Restore；
- Portable Settings Backup / Restore；
- Auto Backup（scheduler / policy / frequency）；
- Backup History UI、Manual Backup UI、Verify UI、Restore UI、Recovery UI、Auto Backup UI；
- Backup retention / delete / 自动清理；
- Web 侧 Backup / Restore。

> Backup V1 为 Database-only 的 Native 实现，不得描述为 Full Backup 或跨平台 Backup。

### 3.13 Device Sync

仅用于同一个用户自己的设备，例如 Windows PC <-> Android Phone。

每台设备有独立本地数据库，通过 Sync Engine 增量同步。

设备是对等 Peer，无默认主设备。IP 不是设备身份。

### 3.14 AI

AI 是嵌入式工具，不作为一级主导航。

未来可能用于：自动标签、总结、Canvas 整理、关系发现、任务提取、日期识别等。

## 5. 平台关系

### Web

与 Desktop 共用 React UI。Phase 1B 建立真实 Web Persistence：SQLite WASM + OPFS + Web Repository Adapter。

### Windows Desktop

使用 Tauri 2 包装共享前端，通过 Rust / Tauri Plugin 获得 SQLite、文件系统、通知、备份、数据迁移等系统能力。

### Android

后续使用 Tauri 2 Mobile 路径发展。Mobile UI 必须单独适配，不把 Desktop 直接等比缩小。Android UI 设计最迟在 Phase 7 正式验收前补齐。

## 6. 数据原则

- Native 核心事实来源：SQLite；
- Web 核心事实来源：浏览器本地 SQLite WASM + OPFS；
- 每个平台维护自己的本地数据；
- Repository Interface 对上层保持一致；
- Attachment 保存实际文件，数据库保存 metadata；
- 多设备绝不直接共享同一实时 SQLite 文件。
