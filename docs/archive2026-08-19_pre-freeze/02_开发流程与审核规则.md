# 02｜开发流程与审核规则

版本：V1.0  
日期：2026-08-19

## 1. 总体流程

所有开发任务统一采用：

Plan → Review → Implement → Test → Review

具体流程：

读取资料  
↓  
Agent 复述需求理解  
↓  
用户审核  
↓  
Agent 提交实施计划  
↓  
用户审核  
↓  
开始编码  
↓  
测试  
↓  
修复  
↓  
重新测试  
↓  
设计稿对照  
↓  
提交开发报告  
↓  
用户人工验收  
↓  
DONE

## 2. 第一步：读取需求

收到新任务后，不要立即修改代码。

先读取：
- project_rules.md
- 当前 Phase 文档
- 最新 UI 规范
- 最新技术规范
- 当前模块设计图
- 当前模块已有代码
- 相关数据模型
- 相关测试

然后输出：

```text
【需求理解】

本阶段目标：

涉及模块：

需要新增：

需要修改：

明确不处理：

依赖：

风险：

需要确认：
```

等待用户确认。

## 3. 第二步：实施计划

需求确认后，仍然不要立即写代码。

提交：

```text
【实施计划】

Step 1：
Step 2：
Step 3：

预计新增文件：

预计修改文件：

预计数据库变更：

预计新增测试：

预计运行命令：

可能风险：

需要用户批准：
```

以下内容若涉及修改，必须单独请求批准：
- 技术栈
- 核心架构
- 数据库核心 Schema
- UI 基础规范
- 公共接口
- Phase 边界

## 4. 第三步：开始实现

只有用户明确回复类似“计划通过，可以开发”才允许正式修改代码。

开发时：
- 只改当前任务需要的内容
- 不顺手重构无关模块
- 不提前做未来 Phase
- 不自行添加新产品功能

## 5. 第四步：测试

编码完成后必须根据当前 Phase 执行适用测试：
- TypeScript 类型检查
- Lint
- Unit Test
- Component Test
- Repository / Integration Test
- Web Build
- Web Preview
- Playwright E2E
- Tauri Check / Build
- Rust cargo test
- Windows Smoke Test
- Android Smoke Test（涉及时）

## 6. 第五步：失败处理

测试失败时禁止直接宣布完成。

必须：

失败 → 分析原因 → 修改 → 重测

无法解决时输出：

```text
【阻塞问题】

失败项目：

错误信息：

已经尝试：

判断原因：

可选方案：

推荐方案：

需要用户决定：
```

然后停止继续扩展开发。

## 7. 第六步：UI 实际检查

涉及 UI 的任务必须实际运行页面。

至少验证：
- 1920 × 1080
- 1440 × 900

检查：
- Sidebar
- Topbar
- 页面 Padding
- 字体层级
- 间距
- Card
- Table
- Modal
- Drawer
- Hover
- Focus
- Loading
- Empty
- Error
- 滚动
- 溢出

## 8. 第七步：设计稿对照

必须再次查看当前模块设计图。

输出：

```text
【设计稿对照】

整体布局：
通过 / 有差异

组件尺寸：
通过 / 有差异

字体层级：
通过 / 有差异

颜色：
通过 / 有差异

间距：
通过 / 有差异

交互：
通过 / 有差异

响应式：
通过 / 有差异

需修复项：
```

明显差异先修复，再提交用户。

## 9. 第八步：开发报告

每轮结束必须输出：

```text
【本轮开发报告】

一、本次目标

二、已完成内容

三、新增文件

四、修改文件

五、数据库变更

六、测试结果

Type Check：
Lint：
Unit Test：
Integration Test：
E2E：
Web Build：
Tauri：
Rust Test：

七、UI 验证

1920×1080：
1440×900：

八、已知问题

九、技术债

十、风险

十一、建议下一步
```

任何未实际运行项必须标记“未验证”或“本阶段未涉及”。

## 10. 第九步：人工验收

提交开发报告后停止。

等待用户查看页面、点击功能、检查数据、检查 UI、检查测试报告。

用户回复“审核通过”后才算 DONE。

## 11. 文件和图片输入规则

### 长期文档
适合作为长期上下文：
- project_rules.md
- 项目说明
- 开发流程
- Phase 计划
- 测试规范
- UI 规范
- 技术架构规范

### UI 图片
开发时不要一次输入所有设计图。

建议：
- 一次 1–3 张
- 同一模块最多约 4 张
- 每张图明确职责

示例：

```text
图片1：Task 主页面布局参考
图片2：Task Drawer 详情参考
图片3：Task Modal / 状态参考
```

收到图片后必须先回复：

```text
【UI 图片理解】

图片1用途：
主要布局：
主要组件：

图片2用途：
主要布局：
主要组件：

规范来源：

存在的不确定项：
```

用户确认后再实现。

## 12. 文档版本规则

如发现 UI规范 V1.0 / UI规范 V1.1，必须使用最新批准版本。

旧版只作为历史参考，不得混合执行。

## 13. Git 规则

建议流程：

feature → test → fix → review → approved → commit

示例：

```text
feat(task): complete task module MVP
feat(canvas): implement canvas editor foundation
fix(task): correct overdue calculation
```

## 14. 删除规则

需要删除重要内容时先报告：

```text
需要删除：
原因：
影响：
替代方案：
```

等待用户确认。

## 15. 决策边界

Agent 可以自主决定：
- 小型代码实现细节
- 命名微调
- 局部函数拆分
- 测试代码组织

必须请求用户决定：
- 新功能
- 产品逻辑变更
- 技术栈变更
- 数据库核心模型变更
- UI 结构变更
- 同步策略变更
- Phase 顺序变更
